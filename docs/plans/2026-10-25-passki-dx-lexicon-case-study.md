# PassKi developer experience: the Lexicon case study

**Date:** 2026-10-25 · **PassKi version:** 0.1.0-alpha04 · **Integration:** Lexicon (KMP: Android, iOS, wasmJs) + its backend (Spring Boot, webauthn4j 0.30)

This document records what it took to add passkeys to a real production app with PassKi. Each friction point
becomes a concrete proposal for the API, docs, tooling or release process. The goal is for PassKi to feel like RevenueCat
or SimpleWebAuthn: one obvious way to do each thing, a good error when you get it wrong, and no glue code that every
app rewrites.

It is the **second round** of feedback. Round 1 (the first integration, 2026-10-24) already shipped in 0.1.0-alpha04:
`passkiOrigin`, the webauthn4j snippet fixes, `passki-test` exposing coroutines, the "Sign in with a passkey" button
guidance, path D (no plugin) and the provisioning-profile note. They are listed at the end so they aren't raised
again.

---

## 1. TL;DR

| | Verdict |
|---|---|
| **Client API** | Strong. `Passkeys()` with no Activity or UIWindow, typed `PasskeyError`, `checkId` and `fixHint` are the best parts. Web support in alpha04 needed **zero** Lexicon code changes. |
| **Testing** | Excellent. `FakePasskeys` produces real ES256 responses that webauthn4j accepts, so the server got real round-trip tests for free. |
| **Server side** | The biggest gap. PassKi stops at "your server checks the response". Lexicon wrote **~650 lines** of server code for this. |
| **Setup and diagnosis** | Tooling is good, but Lexicon (built by PassKi's own author) used **none** of it: no Gradle plugin, no `PasskeyDoctor`, no `passkiCheck`. The tooling assumes you adopt the plugin; a "bring your own server" app doesn't find its way in. |
| **Hardest bug** | The Android emulator fails every passkey creation with AND-03 even when the setup is correct. The hint sent us chasing the wrong cause for hours. |
| **Release process** | alpha04 was tagged but not released on Maven Central, so Lexicon's CI couldn't resolve it. Fixed since (`ed89c7c`), but the README badge still says alpha03. |

**Top 5 changes, in order of impact:**

1. A **server artifact** (`passki-server`, JVM) with the relying-party logic, challenge store, origins and well-known
   JSON, plus shared WebAuthn JSON types. (Section 5.1)
2. A **`SignInMode` that does the right thing for an optional passkey button**, including the Chromium fallback, so
   apps stop copying a capability check + retry. (Section 4.1)
3. **`rpId` and `userHandle` on the results**, and `userHandle` instead of `userId` in the signals API. (Sections 4.2, 4.3)
4. **Logging and a debug mode** like RevenueCat's `logLevel` / `logHandler`, so `Misconfigured` errors show up in
   logcat with their fix without each app writing a log line. (Section 4.5)
5. **AND-03 that tells the truth**: include the running app's SHA-256 and origin, and say when the device is an
   emulator that can't validate the RP ID. (Section 6.1)

## 2. What Lexicon built

Passkeys are an *extra* sign-in. Accounts are still created with Google or Apple; a signed-in user adds a passkey in
Settings and later signs in with it from the auth screen.

| Area | Lexicon code | PassKi used |
|---|---|---|
| Device ceremony | `PassKiAuthenticator` (~90 lines) behind a domain `IPasskeyAuthenticator` | `Passkeys`, `SignInMode`, `PasskeyError`, `signals` |
| Client network + repo | Remote data source, repository, 5 use cases, ViewModel, Settings sheet (~650 lines in total on the client) | none (by design) |
| Server | Options, verification, challenge store, DTOs, well-known controller, origin config, account labels, migration (~650 lines) + 290 lines of tests | `passki-test` in tests only |
| Web (wasmJs) | Nothing: alpha04 just worked | `Passkeys()` on `navigator.credentials` |
| Tests | Client: `PassKiAuthenticatorTest` on `FakePasskeys`. Server: `PasskeyServiceTest` with real round trips | `FakePasskeys`, `TestOptions`, `FakeSignal` |
| Setup | Well-known files generated by the server from config, iOS entitlement by hand | nothing (no plugin, no Doctor, no passkiCheck) |

**Timeline:** 8 client commits and 4 server commits, all within 2026-10-24/25.

## 3. What worked well (keep it)

These are the parts to protect while changing everything else.

- **`Passkeys()` with no platform handles.** The single best DX decision. It made a clean domain interface possible
  and kept the DI module to one line: `single<IPasskeyAuthenticator> { PassKiAuthenticator() }`.
- **Options JSON in, response JSON out.** The server sends options as a JSON tree; the app never models them. PassKi
  accepts the `{"publicKey": ...}` wrapper too. No mapping layer.
- **Typed errors with `checkId` and `fixHint`.** Mapping `Misconfigured` to its own domain error
  was possible only because PassKi separates "your setup is wrong" from "the device can't".
- **`FakePasskeys` on the JVM server.** The server's `PasskeyServiceTest` does real register and sign-in round trips
  against webauthn4j. Most WebAuthn libraries leave you hand-crafting CBOR. This is a differentiator: say so louder.
- **Web for free.** Upgrading to alpha04 needed a version bump and two comment changes. That is what "multiplatform"
  should feel like.
- **Signals.** `unknownCredential`, `acceptedCredentials` and `currentUserDetails` are rare in any SDK. Lexicon used all
  three.
- **The README.** Paths A–D, "Words used here" and the button guidance are clear. The `ImmediateOnly` section prevented
  the "QR code for first-time users" bug before it happened.
- **CHANGELOG discipline.** Every change listed, with the reason.

## 4. Client API

### 4.1 An optional passkey button needs three steps that every app will copy

**What happened.** The README recommends:

```kotlin
val mode = if (passkeys.capabilities().immediateSignIn) SignInMode.ImmediateOnly else SignInMode.Modal
```

On the web, Chromium reports `immediateGet` in `getClientCapabilities()` but then rejects `mediation: "immediate"` as an
unknown enum value. PassKi surfaces that as `InvalidOptions`, so web sign-in failed with "Passkey didn't work". Lexicon
added a retry:

```kotlin
var result = passkeys.signIn(optionsJson, mode)
val rejected = (result as? PasskeyResult.Failure)?.error
if (mode == SignInMode.ImmediateOnly && (rejected is PasskeyError.InvalidOptions || rejected is PasskeyError.NotSupported)) {
    result = passkeys.signIn(optionsJson, SignInMode.Modal)
}
```

**Problems:** the documented pattern is broken on the most common browser; the fix is a platform quirk the app
shouldn't know about; and `InvalidOptions` wrongly suggests the server's options are bad.

**Proposal.**

- Add `SignInMode.PreferImmediate` (name open: `DeviceFirst`, `LocalFirst`): "use `ImmediateOnly` where it really
  works, otherwise `Modal`". PassKi does the capability check and the fallback internally, on every platform.
- Inside the web implementation, treat a `TypeError` for the `mediation` enum as "immediate isn't supported": map it to
  `NotSupported`, never `InvalidOptions`, and cache that `immediateSignIn` is false for the session.
- Update the README snippet to one line: `passkeys.signIn(options, SignInMode.PreferImmediate)`.
- Let `FakePasskeys` simulate the quirk (`FakePasskeys(platform = FakePlatform.Chromium)` or a
  `immediateSignInLies = true` flag), so apps can test it without hand-writing a Chromium error message.

### 4.2 The results don't say which RP ID they belong to

**What happened.** After sign-in, Lexicon needs the RP ID for signals (forget a passkey the server no longer knows).
`PasskeyAssertion` has no `rpId`, so Lexicon re-parses the options JSON with kotlinx-serialization:

```kotlin
private fun rpIdOf(optionsJson: String): String {
    val options = Json.parseToJsonElement(optionsJson).jsonObject
    val publicKey = options["publicKey"]?.jsonObject ?: options
    return publicKey["rpId"]?.jsonPrimitive?.content.orEmpty()
}
```

PassKi already parsed exactly this. Worse, the comment above it ("PassKi already refused options without an RP ID")
stopped being true in alpha04: on the web the RP ID may be left out, and this returns `""`.

**Proposal.** Add `rpId: String` to `PasskeyAssertion` and `PasskeyRegistration`: the RP ID from the options, or on the
web the one the browser used (the page's effective domain). The constructors are already `@InternalPasskiApi`, so this
is non-breaking.

### 4.3 Signals say `userId` but mean the WebAuthn user handle

```kotlin
suspend fun acceptedCredentials(rpId: String, userId: String, credentialIds: List<String>)
```

In an app, "user id" means the account id. Here it must be the base64url WebAuthn user handle (`user.id` from the
creation options), which Lexicon deliberately keeps random and separate from the account id. Passing the account id
"works" without an error and silently does nothing, or leaks an internal id to the credential provider.

**Proposal.**

- Rename the parameter to `userHandle` (keep `userId` as a deprecated named-argument alias for one release).
- KDoc: "base64url user handle, the `user.id` of the creation options; never your account id or email".
- Consider small value classes for the base64url strings (`CredentialId`, `UserHandle`), or at least validate base64url
  and return `InvalidOptions` with a hint when the input isn't.

### 4.4 Converting `PasskeyResult` needs a `when` every time

Every app with its own result type (Lexicon's `Try<T>`, `kotlin.Result`, Arrow's `Either`) writes the same adapter:

```kotlin
private inline fun <T, R> PasskeyResult<T>.toTry(ceremony: String, transform: (T) -> R): Try<R> = when (this) {
    is PasskeyResult.Success -> Try.success(transform(value))
    is PasskeyResult.Failure -> Try.failure(error.toDomain(ceremony))
}
```

**Proposal.** Add the standard set: `fold(onSuccess, onFailure)`, `mapError`, `recover`, `isSuccess` / `isFailure`,
`errorOrNull()`, and `toResult(): Result<T>` (failure wrapped in `PasskeyException`). With `fold`, the adapter above is
one line.

### 4.5 No logging: every app writes its own `Misconfigured` log line

Lexicon logs setup failures itself so they can be found in logcat:

```kotlin
val hint = (this as? PasskeyError.Misconfigured)?.let { " fix=${it.fixHint} check=${it.checkId}" }.orEmpty()
logPlatform(TAG, "Passkey $ceremony failed: $this$hint")
```

Without that line, an AND-03 in a release build is invisible: the user sees "Passkeys aren't working right now" and the
developer sees nothing. RevenueCat solves this with `Purchases.logLevel = LogLevel.DEBUG` and a pluggable
`Purchases.logHandler`, and its debug logs are written to be read by a developer.

**Proposal.**

- `PassKi.logLevel` (`Error` by default, `Debug` in development) and `PassKi.logHandler` to route into Timber, Kermit,
  Crashlytics or `println`.
- At `Error`, log every `Misconfigured` and `Unknown` once, with check ID, fix and docs link. At `Debug`, log each
  ceremony: mode, RP ID, capabilities used, platform error type and how it was mapped.
- Never log challenges, credential ids in full, user handles or response JSON (truncate or hash). Write that rule into
  CONTRIBUTING.
- `Misconfigured.toString()` should include `docsUrl` (it has the hint but not the link today).

### 4.6 Every app writes the same error → UI mapping

Lexicon's mapping (`PassKiAuthenticator.toDomain`) will be the same in most apps:

| PassKi error | Lexicon shows |
|---|---|
| `Cancelled`, `Interrupted` | nothing |
| `NoCredentials` | neutral notice: "No passkey on this device yet" |
| `AlreadyRegistered` | notice |
| `NotSupported` | hide the passkey actions |
| `Misconfigured` | "Passkeys aren't working right now" (our fault, not the device's) |
| `InvalidOptions`, `Unknown` | generic failure |

**Proposal.**

- Add `PasskeyError.isUserCancellation` (true for `Cancelled` and `Interrupted`) and a coarse `category`
  (`UserAction`, `NoCredential`, `Unsupported`, `Setup`, `Unexpected`).
- Publish this table in the docs as "What to show users", RevenueCat-style: one row per error with *what to show*, *what
  to log*, *retry or not*. Today the README only covers `Cancelled` and `NoCredentials`.

### 4.7 Signals: best effort, but reported as failures

Signals often return `NotSupported` (iOS before 26, some Android providers). Every caller ignores the failure. Lexicon
also calls two signals back to back when Settings opens (`acceptedCredentials`, then `currentUserDetails`).

**Proposal.**

- Add `signals.syncAccount(rpId, userHandle, credentialIds, name, displayName)`: one call for "here is the current
  truth about this account", running both signals and skipping what the platform can't do.
- Document that `NotSupported` from signals is expected and should never reach the user. A return type such as
  `SignalOutcome.Applied / Ignored(reason)` would say that in the type system.

### 4.8 A ViewModel-friendly sign-in helper

`passki-compose`'s `rememberPasskeySignIn` handles double taps and drops `Cancelled`, but it is Compose state. Apps with
MVVM (Lexicon's `BaseViewModel`, or any Android ViewModel) can't use it and re-implement the same guard.

**Proposal.** Move the logic to `passki` core as a plain class (`PasskeySignInController` or
`Passkeys.signInOnce(...)`): one request at a time, joins a running request, filters cancellation. The Compose helper
then wraps it.

### 4.9 Small items

- `capabilities()` is `suspend` and Lexicon calls it twice per sign-in. Document whether it is cheap or cached, or cache
  it per process.
- `FakePasskeys.failNextWith` takes a `PasskeyError`; a `failNextWith(platformError = ...)` that goes through the real
  mapper would test the mappers instead of bypassing them.

## 5. Server side: the biggest gap

PassKi says, correctly, that it never talks to your server. But the server half is where most of the work and most of
the security risk is. Lexicon's server needed:

| Piece | Lines | Notes |
|---|---|---|
| `PasskeyService` | 263 | Options, verification, user handle generation, credential record mapping |
| `PasskeyChallenges` | 60 | Single-use challenges bound to ceremony and user, TTL, size limit |
| `PasskeyDto` | 84 | `PublicKeyCredentialCreationOptions` / `RequestOptions` JSON as data classes |
| `PasskeyController` | 89 | 6 endpoints, rate limiting on the public one |
| `PasskeyWellKnownController` | 38 | `assetlinks.json` and `apple-app-site-association` from config |
| `AppProperties.PasskeyConfig` | ~40 | RP ID, origins, `android:apk-key-hash` computation |
| `PasskeyAccountName` | 19 | Account label, avoiding Apple's private-relay email |
| Entity, repository, migration | ~80 | |

Some of it is the kind of code that is easy to get subtly wrong:

- `CredentialRecordImpl(NoneAttestationStatement(), uvInitialized, backupEligible, backupState, signCount, attested, null, null, null, transports)`: ten positional arguments.
- webauthn4j throws `NullPointerException` and `IllegalArgumentException` on malformed input, so every parse needs a
  `catch (RuntimeException)` (round 1 put this in the snippet; every app still has to copy it).
- Challenge binding: a registration challenge must be tied to the user it was issued for, or one account's response
  could register a passkey on another.
- The Android origin formula (`android:apk-key-hash:` + base64url of the SHA-256) lives in app config code.

The plugin's `build/passki/server-snippets/` helps only if you run `passkiSetup`, and a snippet is code you own and
maintain forever.

### 5.1 Proposal: `passki-server` (JVM)

Model it on SimpleWebAuthn, which has a browser package and a server package that share types. A thin, opinionated
layer over webauthn4j:

```kotlin
val rp = PasskiRelyingParty(
    rpId = "example.com",
    rpName = "Example",
    android = AndroidApps(packageName = "com.example.app", sha256 = listOf("AB:CD:...")), // origins derived
    extraOrigins = listOf("https://app.example.com"),
    challenges = InMemoryChallengeStore(ttl = 5.minutes), // or your own ChallengeStore (Redis, DB)
)

// Registration
val options: String = rp.creationOptions(user = PasskeyUser(handle, name, displayName), exclude = existing)
val credential: NewCredential = rp.verifyRegistration(responseJson, expectedUserHandle = handle) // PasskeyVerification.Failure on any problem
// → persist credential.id, publicKey (bytes), signCount, backupEligible, backupState, transports

// Sign-in
val requestOptions: String = rp.requestOptions()
val verified = rp.verifySignIn(responseJson, lookup = { credentialId -> repository.find(credentialId)?.toStored() })
// → update signCount / backupState / lastUsedAt

// Well-known files, from the same config, so they can never disagree with the origins
rp.assetLinksJson(); rp.appleAppSiteAssociationJson(iosAppIds = listOf("TEAM.com.example.app"))
```

Design rules:

- **Never throws on bad input.** Returns a typed failure (`Expired`, `UnknownCredential`, `BadSignature`, `Malformed`,
  `WrongUser`), so a 400 vs 404 vs 401 is the app's choice and no app returns a 500 by accident.
- **Stored credential is a plain data class** the app persists however it likes. No JPA, no Spring in the core.
- **Challenges bound to ceremony and user by default.**
- **`passki-server-spring` (optional, later):** auto-configuration from `passki.*` properties, the two well-known
  endpoints and a `ChallengeStore` bean. Lexicon's well-known controller and config would disappear.
- **A `server-config` endpoint helper** that returns `{"rpId", "origins"}` in the shape `passkiCheck` already reads
  (`server.configUrl`), so SRV-01..03 work for apps that don't use the plugin's generated code.

### 5.2 Proposal: a documented backend contract

Lexicon had to invent the shapes of everything around the four core calls. Most apps will need the same:

- `GET /passkeys` returning the list **plus** what signals need: `rpId`, `userHandle`, `accountName`,
  `accountDisplayName` (Lexicon's `PasskeyListDto`).
- `DELETE /passkeys/{id}`, then `signals.unknownCredential` on the device.
- Sign-in with a deleted passkey: answer **404**, so the app knows to call `unknownCredential` (Lexicon does this).
- Which endpoints need auth, and which public one needs rate limiting (sign-in options).

Publish it as "Recommended server API" with the request and response shapes, and use it in `passki-demo` and the
`passki-server` examples so the whole stack shares one contract.

### 5.3 Proposal: "Choosing user name and display name"

Lexicon learned that the account label shown in the passkey picker matters:

- Apple sign-in users often have a `@privaterelay.appleid.com` email; showing it as `user.name` is useless to them.
- `user.id` (the user handle) must be random, stable per account and never the account id or email.
- One handle per account, so a second passkey shows up as the same account in the provider.

A short docs section (or a `PasskeyUser.forAccount(email, name)` helper in `passki-server`) would save every app this
discovery.

## 6. Setup and diagnosis

### 6.1 AND-03 on the emulator: the most expensive bug

**What happened.** On the Pixel 9 Pro Fold AVD (Play services image, signed in, screen lock set), every passkey
creation failed with Play services 50152 "RP ID cannot be validated" → `Misconfigured`, AND-03. The hint says to list
the app in `assetlinks.json`. We tried screen lock, cache headers, `asset_statements` in the manifest and the Digital
Asset Links API (which confirmed the domain *was* linked). None of it mattered. PassKi's own sample on its own demo
domain failed the same way on that AVD. On a real phone it worked.

**Proposal.**

- When the device is an emulator (`Build.FINGERPRINT` / `Build.HARDWARE` checks), append to the AND-03 hint: "Some
  emulator images can't validate RP IDs even when assetlinks.json is correct. If PasskeyDoctor passes AND-01 to AND-04,
  try a real device."
- Put the AVD limitation in `docs/verified-on.md` and in `docs/checks/AND-03.md` under "Still failing?".
- Make the hint **evidence-based**: PassKi can read the running app's signing certificate. Put its SHA-256 and the
  matching `android:apk-key-hash:` origin straight into the AND-03 message, so the fix can be copied from logcat or
  Crashlytics. This also catches the Play App Signing case (a step that is easy to forget before the first Play release)
  without the developer ever opening Play Console.

### 6.2 The tooling assumes you adopt the plugin

Lexicon serves its well-known files from the server (generated from the same config as the accepted origins, so they
can't drift), and set the iOS entitlement by hand. Nothing in path D points to the tooling that would still help:

- `PasskeyDoctor` works without the plugin, but path D never mentions it.
- `passkiCheck` would check the live domain, AASA and Xcode entitlements in CI, but only through the plugin, whose main
  job (generating and uploading files) Lexicon doesn't want.

**Proposal.**

- Path D, step 6: "In debug builds, log `PasskeyDoctor.run(rpId)` at startup" with a three-line snippet.
- A check-only mode: `passki { rpId = "..."; checkOnly() }`, or a standalone CLI / `npx passki check example.com`, so
  any project can gate CI on the live domain without `passkiSetup`.
- A `PasskeyDebugOverlay` composable (like RevenueCat's debug overlay) for debug builds: Doctor report, capabilities,
  last error with fix and docs link.

### 6.3 Choosing the RP ID deserves its own section

Lexicon first used its company's apex domain, then moved to the app's own subdomain because the apex also listed
another project's apps. **Changing the RP ID orphans every passkey already created.** The README defines "RP ID" but
doesn't help choose one.

**Proposal.** A "Choosing your RP ID" section: it can't change later; apex vs subdomain; one RP ID per product, not per
company; the web app must be on that domain or a subdomain; and the well-known files must be on the RP ID host exactly.
`passkiSetup` could print a one-time warning when the RP ID looks like an apex shared with other apps.

### 6.4 Hosting gotchas worth a "Good to know" line

- An SPA catch-all that answers `/.well-known/*` with `index.html` and status 200 (if AND-01/02 don't already name this
  case, the message should).
- A web deploy that mirrors the build folder (deleting extra files) wipes well-known files kept in the web dist; serve them from the server
  or keep them out of the dist folder.

## 7. Release and docs process

| Issue | Proposal |
|---|---|
| alpha04 was tagged and uploaded `USER_MANAGED` but not released, so consumers' CI failed to resolve it (fixed by `ed89c7c`) | Release workflow ends by polling `repo1.maven.org` until the POM resolves, and fails otherwise |
| README version badge still says `0.1.0-alpha03` | Use a live Maven Central badge (shields.io `maven-central/v`) instead of a hardcoded one |
| Four artifacts plus a plugin, versions kept in sync by hand | Publish a BOM (`passki-bom`) and show `platform(...)` in Install |
| API reference only via `./gradlew dokkaGenerate` | Host Dokka output on `passki.alirezaiyan.com/api/` per version |
| Breaking changes are allowed in alphas | Keep it, but add a "Migrating from X" block per CHANGELOG entry once there are external users |
| Docs examples are compiled in CI (great) | Also compile the *recommended patterns* (button, error table, logging) as one small sample module, so a pattern like the `ImmediateOnly` snippet is tested on every platform, including web |

## 8. Benchmark: what developers praise in RevenueCat (and SimpleWebAuthn)

| RevenueCat / SimpleWebAuthn does | PassKi today | Gap |
|---|---|---|
| One configure call, one entry point | `Passkeys()`, no handles | ✓ none |
| `logLevel` + `logHandler`, readable debug logs | none | **4.5** |
| Error codes with a docs page each and a "what to do" table | `checkId` + `docsUrl` for setup errors | Add a "What to show users" table for all errors (**4.6**) |
| Debug overlay in the app | `PasskeyDoctor` (code only) | **6.2** |
| The backend is done for you (RevenueCat) / a server package sharing types with the client (SimpleWebAuthn) | Snippets via the plugin | **5.1, 5.2** |
| Coroutine **and** `Result` / callback flavours | `PasskeyResult` with `onSuccess` / `onFailure` / `getOrThrow` | `fold`, `toResult` (**4.4**) |
| Test helpers | `FakePasskeys`, real signatures | ✓ ahead of both |
| Hosted, versioned API reference | Generate locally | **7** |
| Sample apps per platform | Compose sample with Demo, Lab, Setup tabs | ✓ |
| Changelog with migration notes | Detailed changelog | Add migration blocks later |

The pattern behind RevenueCat's reputation: **the SDK owns the hard, boring parts end to end**, and when something is
misconfigured it tells you in the log, in plain words, before your users notice. PassKi already has the second half
(check IDs); the first half (server, logging) is the remaining gap.

- webauthn4j snippet: `ServerProperty.builder()`, `RuntimeException` guards around parsing.
- `passki-test` exposes `kotlinx-coroutines-core` as `api`.
- README: the "Sign in with a passkey" button section, testing your server, path D.
- `docs/setup.md`: by-hand setup, origin formula, App Store provisioning profile regeneration, Apple CDN cache.
