# DX Comparison (measured 2026-10-20)

| Metric | passkeys-kmp 0.2.0 | webauthn-kmp | PassKi target |
|---|---|---|---|
| Consumer dependencies | 1 (`passkeys`) for the client; 2 with Compose helper (`passkeys-compose`) | 3 distinct artifacts (4 declarations: `client-flow` + `client-ktor-kotlinx` in commonMain, `client-defaults` in androidMain and iosMain) + app-supplied Ktor `HttpClient`/engine + on Android a Credential Manager provider (`credentials-play-services-auth`); +1 for Compose (`client-compose`) | 1 (`passki`) |
| LOC register + sign-in (with errors) | ~10 for the two `when` blocks in README/sample (`create`/`authenticate` + `Success`/`Failure` branch), but the caller must fetch options JSON and POST `rawJson` to their own backend, which is not counted | ~25-30 estimated: the documented sign-in snippet alone is 14 lines (backend + `PasskeyFlow` construction); register is a symmetric second call; the Compose snippet adds ~10 lines of state handling | <= 15 |
| Manual platform handles | No when using `rememberPasskeyClient()` (Compose only, Android throws if not Activity-hosted). Yes otherwise: `AndroidPasskeyClient(activity)`, Apple anchor (`UIWindow`/`NSWindow`), `HWND` on Windows | Android: pass a `Context` to `defaultPasskeyClient(context)`. iOS: no-arg default, optional anchor provider. Compose helper resolves the current resumed activity per prompt | No |
| Error type | sealed `PasskeyException` (7 subtypes, numeric `code`: DomError, UserCanceled, Interrupted, Unsupported, NoCredential, InvalidPayload, Unexpected); wrapped in sealed `PasskeyResult`. No fix hints | sealed `PasskeyClientError` (UserCancelled, NoCredential, InvalidOptions, Platform, Codec), message only, no throwable retained; `CeremonyResult`/`CeremonyFailure` on top (AlreadyInProgress, Platform). Backend exceptions propagate uncaught. No fix hints | sealed `PasskeyError` + `fixHint` |
| Unified password + passkey | No (no `PasswordCredential`/`GetPasswordOption` found in source) | No (not found in `client/*` or `core/*` source) | Yes |
| Conditional create (upgrade) | Yes, a flag only: `PasskeyCreationOptions.isConditionalCreateRequest`, wired on Android; unclear on other platforms | Not found in client source | Yes |
| Signal API | No (no signal* APIs found) | No (not found; PRF extension helper exists instead) | Yes (Android), iOS via Plan 3 |
| Fake authenticator for tests | Not shipped to consumers. `SoftwareAuthenticator` exists only in `passkeys-server` jvmTest; `FakeAndroidCredentialProvider` is an internal test class | Not shipped to consumers. `FakePasskeyClient` is a private class inside `JsonPasskeyClientTest`; consumers can implement the `PasskeyClient` interface themselves | Yes (`passki-test`) |
| Setup diagnostics | None. README documents `assetlinks.json`/AASA/entitlement setup in prose; failures surface as generic `DomError`/`Unsupported` | None in code. Docs include a troubleshooting page and a capabilities page ("probe at runtime"); no programmatic check found | Plan 2 |

## Notes
- passkeys-kmp (AndroidPoet, v0.2.0, MIT): the best raw ergonomics today. A tiny `PasskeyClient` interface (`create`/`authenticate`, each with a JSON-string overload), one sealed result, and a 3-line README demo. Broadest platform reach: Android, iOS, macOS, Windows, Linux, Wasm, JVM.
- passkeys-kmp: the platform handle is solved only through the Compose helper `rememberPasskeyClient()`. Non-Compose users build per-platform clients and supply the anchor themselves. Android's helper calls `error(...)` when not Activity-hosted.
- passkeys-kmp: options are raw WebAuthn JSON strings from the server and the result is `rawJson` to forward. There are no typed models for the ceremony, so the caller does the server round trip by hand. It also ships `passkeys-server` (Ktor + Yubico java-webauthn-server wrapper), which is a real strength for full-stack users.
- passkeys-kmp: error `code` is an opaque Int (1001-1007) with a fixed generic message. Nothing tells the developer what to fix (for example a missing `assetlinks.json`).
- webauthn-kmp (szijpeter, Apache-2.0, pre-1.0): standards-first and modular. Docs claim ~20 public modules (BOM, model, protocol, crypto, server, client). It is rigorous but the consumer path needs several artifacts, a self-built Ktor `HttpClient`, and understanding of `PasskeyFlow`, backend adapters and opaque continuation state before the first sign-in. This is the weakest point against a "1 dependency, <=15 LOC" goal.
- webauthn-kmp: client support is Android and iOS only (Credential Manager / AuthenticationServices). Docs state iOS security-key support is still being hardened. A desktop/CLI POC exists but is experimental.
- webauthn-kmp: its docs are good (quickstart, troubleshooting, capabilities, Compose lifecycle). It has a capability-probing concept, but no setup diagnostics found. Android recreation safety is handled (activity resolved per prompt).
- Neither library ships unified password+passkey sign-in, signal APIs, a consumer-facing fake authenticator, or programmatic setup diagnostics. These are open differentiators for PassKi.
- Method and caveats: read from `--depth 1` clones (README, docs, commonMain sources, samples); no builds run. LOC figures are counted from README/doc snippets, not a compiled minimal app, so the webauthn-kmp number is an estimate. "Not found" means a case-insensitive grep over client/core sources found nothing, and does not prove absence in unreleased branches.
